# 0017 — Open WebUI as a chat UI, with our own Cube MCP server

**Status:** **Partially superseded.** The Open WebUI surface itself was removed
after the Hub UI chatbot (`apps/web` + `hub-api`) proved sufficient. The
`mcp-cube` chart and the `ohdp_mcp` package it runs were *not* meant to go with
it — they were deleted alongside Open WebUI by mistake and later restored —
because the Hub UI chatbot's own agent calls the same MCP server declaratively,
via the `mcp-cube` connection in `apps/api/config/tools.yaml`. This document is
kept as a record of the original decision. The model-backend note about
ADR-0023 is historical; OpenRouter is no longer a deployed backend for a chat
*UI*, though the Hub UI's model picker can still route to it (docs/chatbot.md §4a).

**Extends:** [ADR-0016](0016-chat-agent-tool-surface.md) — the Cube tool surface
is unchanged; at the time this ADR gave it a second transport and front end.
**Relates to:** [ADR-0007](0007-oauth2-proxy-google-sso.md), [ADR-0015](0015-streamlit-over-superset.md)

## Context

`hub-api` serves a chat UI: one static page, a hand-written SSE client, and a
tool-use loop (docs/chatbot.md §3.4, M3.4). It works, and everything *around* the
model — the quota gate, the per-turn `chat_turns` log that is also the eval set
(§7), the citation check on Europe PMC identifiers (§2.3) — lives in code we own
and want to keep.

What it is not is a chat product. Conversation history, model switching, file
upload, prompt library, keyboard shortcuts, mobile layout, RAG over an uploaded
PDF: all of that is either unbuilt or a stub, and none of it is differentiated
work. Open WebUI is the mature OSS implementation of exactly that surface, ships
an official Helm chart, and — since it gained native MCP (streamable HTTP)
support — can call tool servers directly.

The obstacle is the same one ADR-0016 hit: **Cube Core ships no MCP server.** It
is a Cube Cloud Premium/Enterprise feature, and Cube Cloud is out of budget
(ARCHITECTURE.md §1.3). Open WebUI cannot reach the semantic layer without one.

Three options for that gap:

- **`mcpo`, Open WebUI's stdio→OpenAPI proxy, in front of a community Cube MCP
  server.** Two dependencies instead of none, one of them unvetted and sitting in
  the primary safety control. Rejected for the reason ADR-0016 rejected it.
- **Point Open WebUI at Cube's REST API as an OpenAPI tool server.** Cube Core
  publishes no OpenAPI document, and hand-writing one would recreate the tool
  layer anyway — without `CubeQuery` validating on our side.
- **Wrap the existing tool layer in a FastMCP server.** Chosen.

## Decision

**A FastMCP server, `ohdp_mcp`, exposes the four Cube tools over MCP streamable
HTTP.** It is a *transport*, not a reimplementation: every tool delegates to
`ohdp_agent.cube.CubeClient`, and `run_metric_query` / `explain_query` take an
`ohdp_agent.models.CubeQuery`, validated on our side of the wire. The safety
property ARCHITECTURE.md §6 depends on — a caller selects from a bounded set of
measures and dimensions and can never express a raw query — is a property of that
model, so it holds for an MCP client exactly as it holds for the in-process loop.

**It runs the `hub-api` image with the command overridden** (`charts/mcp-cube`).
One image means one `TAG`, no second entry in `build-images.yml`, and no way for
the MCP tool surface and the chat agent's tool surface to be built from different
commits.

**It is ClusterIP-only.** No Ingress, no oauth2-proxy. The only client is Open
WebUI, in the same namespace. A static bearer token (`OHDP_MCP_AUTH_TOKEN`,
generated by `platform-base` and read by both sides) is defence in depth; the
server refuses to start without either a token or an explicit
`OHDP_MCP_ALLOW_ANONYMOUS`.

**Open WebUI is deployed from the official chart** (`open-webui/open-webui`,
pinned), at `chat.open-health-data-platform.org`, with the bundled Ollama,
Pipelines, Tika and Redis subcharts off — none earn their memory against
ARCHITECTURE.md §4's budget on a single node.

**Authentication is Open WebUI's own Google OAuth, not an oauth2-proxy wall.**
This is the one place the platform departs from ADR-0007's pattern, and
deliberately. Dagster, Streamlit and the hub app have no user model worth
integrating with, so a proxy that gates the hostname is the whole story. Open
WebUI *does* have one — accounts, roles, per-user conversation history, per-user
tool-server grants — and behind a proxy wall it would authenticate every visitor
twice and then believe they were all the same anonymous person. Password sign-in
is off (`ENABLE_LOGIN_FORM=false`); OAuth sign-up is on, because with no login
form there is no other way for a first user to exist, and new accounts land in
`DEFAULT_USER_ROLE=pending` — they can sign in and see nothing until an admin
promotes them. That pending role is the equivalent of
`values/oauth2-proxy-app.yaml`'s email allowlist, and it is the only thing
between a public hostname and a metered Anthropic key.

**The model backend is Anthropic through its OpenAI-compatible endpoint.** Open
WebUI speaks OpenAI's API shape and Ollama's; Anthropic publishes a compatible
surface at `/v1`, so this costs no code and bills the key the platform already
uses.

**`hub-api` is not retired.** Its UI, quota gate, literature tools and turn log
stay at `app.open-health-data-platform.org`.

## Consequences

- **There are two chat surfaces**, and they are not equivalent. Open WebUI has no
  quota gate, no `chat_turns` log, no Europe PMC citation check, and no access to
  OpenMetadata context — the OM MCP server is reachable, but wiring it up is a
  separate decision, since §6 makes catalog content untrusted prompt input and
  hub-api is where that is reasoned about. Anthropic's OpenAI-compatible layer
  also does not expose extended thinking. Whether to retire hub-api's UI is a
  later call that should be made on evidence, not on this ADR.
- **Cost control is weaker on the new surface.** hub-api gates on quota before the
  model is invoked; Open WebUI does not. The `pending` default role and the
  Anthropic console's own spend limit are the controls until that changes.
- **Open WebUI's tool-server connection is UI-managed state.** There is no
  environment variable or config file to declare MCP tool servers, so registering
  `mcp-cube` is a manual post-install step (`charts/mcp-cube/templates/NOTES.txt`),
  and rotating the bearer token means re-entering it there. This is the one piece
  of this deployment that is not reproducible from git, and it is worth revisiting
  if Open WebUI grows a declarative option.
- **A fourth Google OAuth client** (`OPENWEBUI_OIDC_CLIENT_ID` / `_SECRET`) with
  redirect URI `https://chat.open-health-data-platform.org/oauth/google/callback`.
  It falls back to Dagster's client, which then needs that URI added in the Google
  console — a console edit, not a deploy step.
- **A fourth Postgres database**, `openwebui`. `platform-base`'s initdb script only
  runs on an empty data directory, so a `postgres-db-bootstrap` Job now creates any
  missing database idempotently on every install and upgrade. That makes
  `postgres.databases` genuinely declarative for the first time — previously,
  adding an entry to it did nothing on a live cluster.
- **~1.2 GB more memory** (Open WebUI 1 GB, mcp-cube 256 Mi) against
  ARCHITECTURE.md §4's ~13 GB steady state. The disabled subcharts are what keeps
  that from being ~2.5 GB.
- **If Cube Core ever ships an OSS MCP server**, `ohdp_mcp` is the thing to delete
  — the tool contracts stay, only the implementation behind them changes.
