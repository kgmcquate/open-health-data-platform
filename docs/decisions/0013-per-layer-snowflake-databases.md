# 0013 — One Snowflake database per medallion layer

**Status:** Accepted
**Relates to:** amends the naming scheme [ADR-0012](0012-native-snowflake-tables.md)
carried forward from [ADR-0010](0010-iceberg-medallion-lakehouse.md) —
ADR-0012 explicitly kept `raw_<source>` / `clean_<source>` / `core` /
`mart_<name>` schema names inside one `OHDP` database "unchanged"; this ADR
changes that.

## Context

The medallion layer was encoded entirely in the schema name, inside a single
`OHDP` database: `raw_healthdata_gov`, `clean_healthdata_gov`, `core`,
`mart_respiratory`. That's workable at one source and one mart, but the
layer and the source/mart name were concatenated into a single string doing
two jobs at once, and every consumer (Snowsight's object tree, a grant, a
`SHOW SCHEMAS`) saw all four layers flattened into one list with no
structural separation between them.

## Decision

Split the single database into three, one per layer, and let the schema name
carry only the source or mart:

- `RAW.<source>.<table>` — dlt's raw loads, append-only.
- `CLEAN.<source>.<table>` — dbt's typed, deduped staging models.
- `CURATED.<mart>.<table>` — dbt's presentation-layer marts, plus the
  always-present `CURATED.core` for conformed, cross-source models (the old
  bare `core` schema, relocated rather than dropped — it was never a fourth
  layer, just presentation-layer data with no single mart owner).

`ohdp_ingestion/naming.py` is still the one place this is encoded:
`database(layer)` returns `RAW`/`CLEAN`/`CURATED`, `schema(layer, source)`
returns the source or mart name alone, and `namespace()` composes the two for
display (Dagster asset metadata, docstrings). dlt's raw loader
(`ohdp_ingestion/healthdata_gov/source.py`) calls both directly; dbt's
`dbt_project.yml` sets a literal `+database` per layer folder alongside the
existing per-folder `+schema`.

**DuckDB (local/CI) does not get the same split.** It's a single-file catalog
with no native multi-database support the way Snowflake has it; forcing
`+database` there would mean `CREATE TABLE "RAW"."schema"."table"` against a
catalog that doesn't exist. `generate_database_name.sql` is new and only
applies the override on `target.type == 'snowflake'` — DuckDB always falls
back to `target.database`, exactly dbt's own default behavior with no
override. The practical effect: locally, `clean`'s dbt models and `raw`'s dlt
tables land in the same schema (e.g. both under `healthdata_gov`) inside one
file, distinguished only by table name, not by a separate catalog. That's a
deliberate, accepted blur in the local/CI dev loop — it doesn't collide (dbt
tracks each source's location explicitly; there's no name overlap), it isn't
new in kind (ADR-0012 already accepted the DuckDB/Snowflake dialect split as
"an accepted, ongoing cost in exchange for a dev loop that stays fast, free
and offline"), and the alternative (multiple attached DuckDB files locally
just to mirror three cloud databases) is not worth the complexity for a
single-source, single-mart project.

The dbt **source** definition for the raw layer
(`_healthdata_gov__sources.yml`, generated by
`scripts/scrape_healthdata_gov.py`) needs the same target-conditional
behavior but isn't routed through `generate_database_name.sql` — a source's
`database:`/`schema:` are taken literally, not macro-computed — so the
generated file inlines the equivalent branch directly as Jinja:
`database: '{{ "RAW" if target.type == "snowflake" else target.database }}'`.

## Consequences

- **Terraform**: `snowflake_database.ohdp` (one resource) becomes
  `snowflake_database.layer` (`for_each` over `{raw, clean, curated}`); the
  `snowflake_namespaces` flat schema list becomes `snowflake_sources` (mapped
  into both `RAW` and `CLEAN`) and `snowflake_marts` (mapped into `CURATED`,
  alongside the always-created `core`). Every grant resource that used to
  target the one database now `for_each`es over the three.
- **No `OHDP_SNOWFLAKE_DATABASE` setting.** The old single-database name was
  a Terraform var → Helm ConfigMap → `Settings.snowflake_database` → dlt
  credential chain. With three fixed, non-configurable database names shared
  by Python (`ohdp_ingestion.naming`) and dbt (`dbt_project.yml`), that
  env-var hop is gone; `settings.py` no longer has a `snowflake_database`
  field, and neither Terraform's outputs nor Helm's `pipelineConfig` mention
  one.
- **Table names are unchanged.** `raw_healthdata_gov__<dataset>` (the
  `raw_table` config field, baked into ~30 generated `defs.yaml` files and
  every dbt `source()` call) still carries the old schema-name-shaped prefix,
  now redundant with the schema it lives in (`RAW.healthdata_gov.raw_healthdata_gov__…`).
  Deliberately out of scope here: renaming it touches the scraper's table
  disambiguation logic, every generated dataset config, and Dagster asset
  keys already referenced by tests — a separate change if wanted.
- **Existing Snowflake objects are orphaned.** `OHDP.raw_healthdata_gov.*`
  etc. are not migrated; re-running the raw loads against the new databases
  is the migration path, same as ADR-0012 accepted for its own predecessor.
